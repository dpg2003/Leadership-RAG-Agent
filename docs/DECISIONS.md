# Decisions

Each entry: what we chose, what we rejected, and why. Newest at the bottom.

## D1. No LinkedIn as a source

- **Chosen:** The company's own site, SEC EDGAR, and one web search API.
- **Rejected:** Scraping LinkedIn (directly or through scraping proxies or APIs that resell its data).
- **Why:** LinkedIn's User Agreement prohibits scraping. We accept the cost: weaker coverage of VPs and department heads, who often appear only there. That gap is measured (coverage-scout, also LinkedIn-free) and listed under "Known misses" in `VALIDATION.md`. The same rule covers any site whose ToS forbids automated access.

## D2. SQLite relational store, not a vector store

- **Chosen:** SQLite with a plain `schema.sql`, committed per company at `data/<domain>/leadership.db`.
- **Rejected:** A vector store or embedding retrieval over raw pages. Also rejected: Postgres as a runtime dependency.
- **Why:** The target questions are structured: filter by role ("who's the CTO"), count ("how many VPs"), and look up a field ("where is the CEO based"). A relational model answers them exactly, while similarity search makes counts and filters approximate. SQLite needs no server, so the repo stays clone-and-go.
- **Postgres compatibility:** The schema avoids SQLite-only features. Booleans are `INTEGER` 0/1, timestamps are ISO-8601 UTC `TEXT`, and enums are `CHECK` constraints. The one swap is that `id INTEGER PRIMARY KEY` becomes `id INTEGER GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY`. Queries in `repository.py` use `?` placeholders, which a Postgres driver would replace with `%s`.

## D3. Resolved view and audit trail are separate tables

- **Chosen:** `facts` stores every claim (field, value, source, evidence snippet). `people` and `roles` store the resolved current view, derived from facts.
- **Rejected:** One `people` table with the source columns inline.
- **Why:** Inline sources can only keep one source per field, so conflicts disappear. With separate facts, the chat agent can show every source and point out disagreements.
- **Enforced in the repository, not just the pipeline:** A fact needs a source and a non-blank snippet (also a DB `CHECK`). `location`, `bio`, and each role's `title_raw` can only be written if a matching fact exists for that person. Otherwise `ProvenanceError` is raised.
- **A person can't exist without evidence.** `upsert_person` takes a source and a snippet and writes the `full_name` fact in the same call. `update_person_resolved` also requires the resolved `full_name` to match a fact. Every fact's source must belong to the person's company.
- `people.profile_url` must be the URL of a row in `sources` for the same company (checked on write), not a separately sourced claim.
- **Facts are rebuilt each run, not accumulated.** Before resolving, `clear_people` deletes the company's people, which cascades to roles and facts. Re-extraction then rebuilds facts from the cached raw documents. The durable record is `sources` plus the raw cache. Rejected: keeping facts across runs. Stale claims from older runs would build up, and conflict handling would need a per-run version, which is too much for this scope.
- Writes go through `Repository.transaction()` (commit on success, rollback on error), so a failed run never leaves a half-resolved company behind.

## D4. Schema details (reviewed with Daniel in Phase 0)

- **Source priority is derived, not stored.** `SOURCE_PRIORITY` in `models.py` maps `sources.source_type` to a priority: company_site (0) beats sec_filing (1), which beats search (2). Rejected: a `facts.source_priority` column, which would duplicate `source_type` and could drift from it.
- **`source_count` is computed in the query** (distinct `source_id` across the person's facts). Rejected: storing it on `roles`, where it could go stale after a re-resolve.
- **No `exec` seniority.** President and General Counsel map to `c_level`, because the 10-K lists them as executive officers. `title_raw` always keeps the original title, so nothing is lost. Allowed seniorities: `c_level | vp | head | founder`.
- **Dedupe key:** `people` is unique on `(company_id, normalized_name)`. `normalize_name` strips accents, case, punctuation, honorifics and suffixes, and middle initials. It deliberately does **not** merge nicknames ("Vlad" vs "Vladimir"). A wrong merge would combine two people's facts, which is worse than a duplicate that shows up in validation.
- **`facts.field`** is restricted to `full_name | title | location | bio`.
- **`collection_runs.stats_json`** holds tokens in and out, cost, document counts per source, people found, and rejected extractions with reasons.
- **Counts are of people, not roles.** A CEO who is also a co-founder counts once in "how many leaders".

## D5. Configuration via environment

- `.env` at the repo root is loaded automatically (`python-dotenv`). Variables: `ANTHROPIC_API_KEY`, `TAVILY_API_KEY`, `SEC_USER_AGENT` (used as-is, e.g. `"Jane Doe jane@example.com"`, as SEC requires), and `LLM_MODEL` (blank means `claude-sonnet-5-5`).
- Only `ANTHROPIC_API_KEY` is needed to run chat, eval, and the UI against the committed data. `TAVILY_API_KEY` and `SEC_USER_AGENT` are only needed for `leadership collect`. A missing key raises an error that names the variable and says where to get it.
